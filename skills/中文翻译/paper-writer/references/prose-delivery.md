# 正文交付纪律

交付物是作者可直接使用的干净正文。产生它的所有规划结构保持内部。本文件定义用户收到什么以及什么永不出现在其中。

## 用户收到什么

- 请求的正文，流畅段落，有来源处使用数字引用 `[1]`、`[2]`。
- 正文含引用标记时，紧跟**参考文献**列表，双向对应编号。
- 可选地，参考文献之后：至多三行白话备注（需作者确认的项、作者应检查的推断、建议的下一步）。无表格、无列表、无标题。如无可说的有用内容，完全省略备注。
- 产品长时（完整草稿、多节），写入工作区文件并指向用户；台账和映射放入独立工作文件，绝不嵌入正文。

## 输出中永不出现在内容

- 命名段落的 Markdown 标题（"第一段：背景"）。
- 类型定位注释（"类型：技术论文"）。
- 一致性检查或门禁结果（"运行示例回路：通过"）。
- 严重性汇总（"3 CRITICAL, 2 MAJOR"）。
- 内部步骤或框架引用（"步骤 5 产生了以下内容"、"基于我构建的思考模板"、"遵循 CER 框架"）。
- 流程前言，任何语言："让我先分析一下……"、"这里我将结构化……"、"首先让我分析一下……"、"根据蓝图……"。直接从正文开始。
- 任何种类的方括号占位标签："citation needed"、"to be verified"、"to be specified by authors"、"to be confirmed"、"user provided"、"model inference"及所有变体。
- Emoji、装饰性加粗和警告框。

这些是脚手架：是思考如何工作的方式，不是作者应读到的内容。发现自己在写一个时，删除并继续写正文。

## 论文正文中的公式、表格和强调

- 显示公式用 `$$...$$`，行内数学用 `$...$`；绝不裸下标或 HTML 标签。公式后的符号解释必须使用公式中使用的确切符号。
- 结构化数据（结果、消融、描述统计）放入表格，不放入流水正文。表格有标题、表头和单位；草稿模式中，无确认数字的值单元格用 `--` 或显式 PLANNING DATA 标记，绝不编造值。
- 论文正文不使用 markdown 加粗或斜体表强调；通过主题句或在会议允许时通过子节标题承载强调。

## 分块交付

如长度迫使分块，标记每块（"第 i 部分，共 N 部分"）并使每块完整且独立可用。绝不交付以完整呈现的部分产品。
