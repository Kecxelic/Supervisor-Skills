在写任何涉及引用、实验或事实判断的正文之前，先理清你实际持有什么证据。本文件是本插件中每个起草技能遵循的纪律。

## 1. 合法来源与证据层级

生成正文中的每个事实性声明恰好有三个合法来源：用户提供的、本会话中检索并验证的、或无争议的领域常识。**模型记忆永不是来源。**

| 层级 | 来源 | 可支撑 | 不可支撑 |
|---|---|---|---|
| **L1 全文/数据** | 用户提供了完整论文、数据、图或日志 | 任何声称 | 无 |
| **L2 摘要** | 用户提供了摘要，或检索返回了摘要 | 研究方向、头条发现 | 具体数字、方法步骤、实现细节 |
| **L3 元数据** | 检索返回了标题、作者、年份、会议 | "X 等（年份）处理了 Y" | 方法细节、性能数字、局限分析 |
| **L0 领域常识** | 从业者不加引用即接受的事实，前提是 (a) 删除该句不削弱论证且 (b) 不含具体数字、人名或量化比较 | 背景框架陈述 | 任何含数字、人名或比较的声称 |
| **L4 模型记忆** | 你仅"记得知道"的任何东西 | **无** | **一切** |

L0 测试：如果你对一句话是否常识犹豫了，它就不是。搜索来源。

## 2. 证据台账

对整篇论文任务，产出证据台账并保留为工作文件。对单节或单段，心算同样盘点，但任何将携带引用的段落必须在起草前确认来源。

```markdown
| ID | 来源 | 层级 | 支撑 | 不可支撑 | 计划用途 | 风险 |
|---|---|---|---|---|---|---|
| E1 | 用户：结果表，results/main.csv:12 | L1 | 方法细节、精确数字 | 无 | Results、Discussion | 无 |
| E2 | 检索：Author（2023），元数据 | L3 | "用 Y 处理了 X" | 方法步骤、数字 | Related Work | 仅元数据 |
| E3 | 用户：摘要片段 | L2 | 发现方向 | 具体数字 | Introduction | 无数字 |
```

填写规则：

- 每来源一行，标明层级。
- **"不可支撑"列为必填**；其作用是在写作时保持来源边界在视野中。
- L3 行携带 `仅元数据` 风险标记。
- L4 永不进入台账。它不是证据。
- 来源是用户工作区中的文件时，记录路径（以及有用的行或表号），使每个声称可追溯到可检视的制品。

## 3. 来源思考（写作时规则）

这是核心反编造机制，在生成文字**之前**运行，不是之后。起草每段之前，内部确定该段将声称什么以及哪个来源（用户输入、检索结果或 L0 常识）支撑每个声称。无来源的声称在规划时排除，不是写下后标记。

直接写干净正文。不在生成文本中嵌入任何来源标记、编辑方括号或待确认注释。同上下文自审查无法可靠地在事后捕捉编造；防御是此写作前检查，加上引用的独立验证通过。

## 4. 无占位标签：唯一解决路径

交付正文绝不包含任何种类的方括号占位符：无"citation needed"、无"to be verified"、无"to be specified by authors"、无"to be confirmed"及任何变体。占位符不是安全阀；它是未完成的工作。

当声称缺少来源时，解决路径固定且无廉价出口：

1. 搜索真实来源（使用会话的文献检索能力）。
2. 找到：织入真实引用。
3. 两三个关键词变体后未找到：重写句子使其不再需要该声称，或删除该句。

如确实需要作者确认，在正文之后用两三行白话说明，绝不嵌入正文中。

## 5. 编造红旗家族

最诱人编造的细节，因此在用户未提供时禁止，分五类：

| 类别 | 示例 | 规则 |
|---|---|---|
| 应用场景 | "光伏农场"、"自动驾驶" | 仅用户命名的场景 |
| 机制与因果故事 | "因为频谱混叠而有效" | 仅用户描述的机制 |
| 量级与规模词 | "数百个类别"、"十倍差异"、"少于十个像素" | 仅用户给的量级 |
| 程序与实现细节 | 量表条目数、知情同意程序、软件版本、beam size、日期、缺失率 | 仅用户陈述的；否则省略 |
| 标识符 | 案例引用号、法条号、标准号、arXiv ID | 仅用户提供或检索确认的标识符 |

通用形式：**用户未提供的具体细节不写，句号。** 省略永远安全于看似合理的编造。

## 6. 实验证据门禁

当正文涉及实验结果、Discussion 或贡献声称时，检查每个门禁：

| 门禁 | 检查 | 失败时 |
|---|---|---|
| D0 数据边界 | 数据来源、样本、划分明确？ | 描述实验计划，非结果 |
| D1 指标定义 | 指标和计算已定义？ | 解释指标目的，无有效性判定 |
| D2 比较 | 基线和消融已识别？ | 将贡献降级为设计动机 |
| D3 结果来源 | 数字来自用户确认的真实运行？ | 草稿模式：对冲措辞（"初步结果提示"）；终稿模式：无有效性声称 |
| D4 污染 | 计划数字与真实数字分开？ | 将计划数据保留在标记为计划数据的表中，绝不作为结果出现在正文中 |
| D5 结论边界 | 结论限于测试条件？ | 删除或限定泛化 |

## 7. 贡献到证据追溯

交付整篇论文前，追溯每个贡献声称：

```markdown
| 贡献 | 方法章节 | 实验/图 | 证据状态 |
|---|---|---|---|
| C1：提出框架 X | 3.1 | Table 2 消融 | L1 已确认 |
| C2：机制 Y | 3.2 | 无 | 不支撑：降级 |
```

无实验追踪的贡献在草稿模式中记录为待验证（不注释在正文中）；在终稿模式中降级或移至 Future Work。

## 8. 真实 vs 计划结果，草稿 vs 终稿模式

- 用户说结果真实且完整：写"我们观察到"、"结果显示"。
- 用户说结果是预期的、计划的或不确定的：写"作者报告"、"初步结果提示"，绝不作为发现呈现。无方括号注释。
- **草稿模式**（默认）：表格中允许结构性占位（标准表骨架，值单元格用 `--`），但正文中的事实性声称遵循上述所有规则。
- **终稿模式**（用户说投稿就绪或 camera-ready）：无任何待处理项；任何未解决项阻止"就绪"声称。
