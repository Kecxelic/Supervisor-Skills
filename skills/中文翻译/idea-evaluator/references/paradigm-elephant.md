## 1. 核心想法

每个研究社区都有它知道重要但系统性回避的问题。有时问题对当前工具集太难。有时不符合发表惯例。有时所有人假设别人最终会解决。如研究者能将其中一个大象形式化为可处理的学术问题，重构常成为新子领域。

猎捕技术是看向学术 benchmark 气泡之外，看向当前方法静默失败的边缘案例。

## 2. 技术A：真实痛点提取

### 程序
1. 识别三位从业者（行业工程师、已部署系统运维者或领域专家）在生产中使用该领域的产出。
2. 问他们：每周遇到的最大痛点是什么，学术文献不处理的？
3. 对每个痛点，问它是研究问题还是工程细节。
4. 对研究级痛点，问：能否形式化为 benchmark、新问题设定或可测量任务？

### 痛点是研究级的信号
- 多位从业者独立提出。
- 当前学术工作隐含假设问题不存在。
- 严格形式化需要新评估指标，不仅是已有格式的新数据集。
- 痛点已稳定至少两年；不是某工具版本的临时产物。

## 3. 技术B：边缘案例编目

### 程序
1. 在真实数据长尾输入上运行领域当前最佳方法。
2. 编目失败模式：按根因分类每次失败。
3. 识别常见、系统且文献未处理的失败模式。
4. 对每个，问：这是 Prompt-Engineering 补丁问题，还是当前范式的根本局限？
5. 对根本局限，提出回应根因的重构。

### 边缘案例是大象的信号
- 频繁：出现在至少 10% 真实输入中。
- 系统性：同类输入一致失败。
- 未处理：文献搜索无直接工作处理此失败模式。
- 根级：快速修复不持久；每个补丁暴露同一失败的下一层。

## 4. 工作示例：大规模模式链接
- **学术 benchmark 焦点**：单表或小模式问题的 Text-to-SQL 评估，列名干净。
- **从业者痛点**：真实数据库有数千表，命名不一致或晦涩；DBA 也不知给定问题该用哪些表。
- **形式化**：大规模模式链接或模式检索作为一等研究问题，有自己的 benchmark 和方法。
- **影响**：检索增强 Text-to-SQL 整个子领域打开，此前在干净模式假设下不可见。

## 5. 工作示例：复杂任务的多代理协作
- **学术焦点**：单一代理 LLM 在短、有界任务上评判。
- **从业者痛点**：复杂真实业务工作流需要跨专业角色协调；单一代理陷入长链、幻觉或循环。
- **边缘案例分析**：失败非随机；与需要持续状态、跨职能专长或回滚恢复的任务相关。
- **形式化**：多代理协作框架或标准操作程序驱动的代理工作流，各有自己的评估协议。
- **影响**：围绕代理编排而非代理智能的新一类论文。

## 6. 应忽略什么
- **工程痛点**："my deployment tool is slow" 对从业者有价值但非研究级。
- **一次性失败**：单个病毒式 bug 不是大象。
- **已形式化的问题**：如文献已有子领域，大象已被捕获。继续前进。
- **下个模型版本可解的痛点**：如预期仅靠扩展就能解决，重构为时过早。
- **超出用户可达的大象**：某些大象需要机构基础设施（行业合作、专有数据）PhD 学生无法独立获取。记录在 Hamming 列表上并推迟。
