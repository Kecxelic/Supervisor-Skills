## 1. 什么算致命

致命缺陷是如果不解决则不论论文其余部分执行多好都会被顶会拒稿的问题。门槛有意设高：并非每个弱点都是致命的。将想法判定为致命缺陷会阻止学生追求它，因此本节使用保守定义。

致命缺陷有三个特征：可在想法描述中观察（不仅在实验中发现）；仅靠更强基线或更好写作无法修复；审稿人会在首轮就标记。

标准数量为每个想法至多两个致命缺陷。如列表超过两个，想法方向本身有问题，需要转向。

## 2. 十个标准致命缺陷

### F1：与最近已有工作无新颖性差异
想法复制或仅微调同一子领域的已发表基线。审稿人框架化为"被已有工作 X 压制"。

### F2：会议不匹配
想法的贡献匹配不同会议。系统贡献投 ICML 即使工作强也常被拒；理论贡献投 VLDB 同样命运。

### F3：基线不是真正的基线
所选基线弱或过时。2026 年用 2023 年基线说服不了任何人；审稿人要求当年 SOTA。

### F4：无令人信服的动机
想法在真实世界中的有用性不清。论文无法回答"谁在意以及为什么是现在"；审稿人称"not motivated"。

### F5：能力不匹配
学生无法在想法生命周期内执行。想法有效但学生缺技能、时间或资源完成，导致错过截止或论文不完整。

### F6：不可验证的声称
想法依赖于计划实验无法验证的经验声称。例："our method works across domains" 但无跨领域实验在范围内。

### F7：伦理或数据获取阻碍
想法需要学生无法获取的数据或人类受试者。IRB 批准缺失；专有数据；隐私约束。基础设施使执行不可能。

### F8：范围过于雄心
想法在贡献列表中承诺太多。例："we propose a benchmark, a new method, theoretical analysis, and a deployed system" 在一篇论文中。每项贡献被其他削弱；审稿人标记为"unfocused"。

### F9：为问题找解决方案
想法从学生想用的技术开始，寻找适合的问题。常产出问题感觉人为、实验不决定性的论文。

### F10：未考虑失败案例
想法将方法视为银弹。无失败讨论、在什么条件下、局限是什么。审稿人标记为过度声称。

## 3. 检测规则

### F1 检测
- 问：此想法相对于最近的单一已有工作添加了什么？
- 红旗：学生无法一句话命名具体贡献，或贡献是"we use a bigger model"或"we combine two existing methods"。

### F2 检测
- 问：目标会议是什么，该会议最近一版的 top three 论文是什么？
- 红旗：想法的贡献类型不在这三篇论文中。

### F3 检测
- 问：最近三个月目标 benchmark 上的最强公开结果是什么？
- 红旗：学生的基线超过 12 个月或未引用 2026 年结果。

### F4 检测
- 问：如这个问题明天解决，谁受益，多少？
- 红旗：答案是"other researchers studying this narrow problem" 而无外部受益者。

### F5 检测
- 运行 references/lifecycle-capability-matching.md 中的匹配逻辑。
- 红旗：两个或以上失配标记触发。

### F6 检测
- 问：什么实验如产生特定结果能证明主要声称？
- 红旗：学生无法设计此实验，或实验超出范围。

### F7 检测
- 问：所有所需数据目前可获取吗？如涉及人类受试者，IRB 批准到位吗？
- 红旗：任何所需资源缺失且无法在想法生命周期内确保。

### F8 检测
- 计数拟议 Introduction 中的贡献要点。
- 红旗：超过四条，或要点跨越不同论文类型（benchmark + 方法 + 理论 + 系统）。

### F9 检测
- 问：学生在实践中遇到过这个问题，还是从想应用的技术开始？
- 红旗：学生无法命名激发工作的具体真实世界失败。

### F10 检测
- 问：方法在什么条件下失败，Limitations 章节的计划是什么？
- 红旗：学生无法命名两种失败模式。

## 4. 防御策略

对每个缺陷，一个具体防御。如防御无法在想法生命周期内执行，缺陷保持致命。

| 缺陷 | 防御 |
|---|---|
| F1 | 一句话定位相对于最近已有工作。命名新想法占优的具体轴 |
| F2 | 要么切换会议目标匹配贡献类型，要么重塑贡献适配原会议 |
| F3 | 识别最新 SOTA 并作为主要基线。如不可获取，记录时间截点并论证 |
| F4 | 在 Introduction 第一段命名具体外部受益者（用户、已部署系统、政策问题） |
| F5 | 遵循生命周期-能力匹配参考中的恢复策略。缩窄范围、合作、重框架类别或转向 |
| F6 | 显式设计决定性实验并放在实验计划顶部。如不可行，转向声称 |
| F7 | 在继续前确保获取。IRB 尽早申请。专有数据确保合作 |
| F8 | 贡献列表缩至两到三条。将剩余项拆分为后续论文 |
| F9 | 从问题侧重启。访谈用户、运行试点研究或记录激发技术的真实失败 |
| F10 | 在开始实验前预注册两种失败模式和 Limitations 章节。在案例研究章节中包含失败案例 |

## 5. 严重性升级逻辑

列出缺陷和防御后，用以下逻辑将每个缺陷转换为严重性标签。

- **CRITICAL**：缺陷在给定当前资源下无法在想法生命周期内防御，或存在两个以上 MAJOR 缺陷。
- **MAJOR**：缺陷需要 2-4 周专门工作来防御。
- **MINOR**：缺陷可在不到一周的写作或文献工作中解决。

判定含义：

- **任何 CRITICAL 缺陷**：判定为拒绝并转向。不追求此版本想法。
- **两个以上 MAJOR 缺陷**：判定为带修订接受。在开始实验前防御所有缺陷。
- **至多一个 MAJOR 和任何 MINOR**：与强接受兼容，视其他评估步骤而定。

## 6. 被数据反驳的机制：最高风险案例

如用户报告的数据或附件**已显示核心机制被基线、消融或简单对照匹配或超越**（如隔离核心机制得分 0.30 对固定基线 0.45），核心声称接近被证伪。

立即视为 CRITICAL 并将判定锁定为拒绝并转向。不可降级为普通问题。此外：

- 被反驳的指标不得作为故事头条；
- 不为它写防御；
- 不编造乐观阈值让它"通过"；
- 最重要的是，绝不描述为"再几个小时或几天实验就能成立"。一个被构建然后输给基线的核心机制是**被反驳的前提**（想法须改变），不是更多努力能填补的缺口。

保持区分清晰：此规则在**数据已经击败机制**时触发，而非机制仅未测试时。一个有扎实机制的未测试想法走另一条路（基于机制的高分加命名的验证实验；打分参考覆盖了它）。不要用此规则扼杀有前途的未测试工作。
