## 1. 为什么 Overview 重要

Solution Overview 图位于方法论章节顶部（通常 Figure 2 或第 3 节首图）。其工作是给跳过正文的读者一个完整的方法心智地图：输入是什么、阶段是什么、输出是什么、组件如何交互。

读者应能在后续技术子节阅读中随时查阅此图并重新定位自己在方法中的位置。

## 2. 范式 A：管线

最常见范式。从左到右（或从上到下）的阶段序列：输入到阶段 1 到阶段 2 到输出。每阶段是命名框；子模块在框内。

### 布局

- 画布：宽，宽为高的两到三倍。
- 三到五个大阶段框从左到右。
- 每阶段框含子模块小框。
- 阶段间箭头表示数据流；标注箭头表示特定数据类型。
- 最左输入；最右输出。

### 何时使用

- 方法是多阶段数据转换。
- 每阶段独立于其他，可单独理解。
- Text-to-SQL 方法、数据清洗管线、代理工作流。

### 典型示例

AFlow（ICLR 2025）Figure 3：三列（Search Space；Search via AFLOW；Search Result），清晰的从左到右流程。

## 3. 范式 B：系统架构

当方法是交互组件系统而非线性管线时使用。大外框代表系统边界；内部框代表组件；箭头表示系统内数据流和控制流。

### 布局

- 画布：方形或略宽。
- 外矩形标注系统名。
- 四到八个内部组件框，按职责排列（前端、后端、数据存储、编排器）。
- 箭头表示消息传递或数据流。
- 按组件类别配色（数据、计算、接口）。

### 何时使用

- 论文呈现多交互代理、模块或服务的系统。
- 组件并发运行而非顺序。
- 反馈环重要（一个组件的输出反馈到另一个）。

### 典型示例

Alpha-SQL（ICML 2025）Figure 3：展示 MCTS 框架，含 LLM-as-action-model、搜索树扩展过程和自监督奖励反馈环。

## 4. 范式 C：多层

当方法有层次结构或根本不同的多阶段（离线 vs 在线、训练 vs 推理、宏观 vs 微观）时使用。

### 布局

- 画布：垂直分为两到三个水平层。
- 每层代表一个阶段或抽象级别。
- 层间箭头展示一层输出如何喂入另一层。
- 层有标注（如"离线"和"在线"，或"训练"和"推理"）。

### 何时使用

- 方法分离预处理和运行时执行。
- 不同组件以不同频率运行。
- 方法有训练阶段和推理阶段，行为不同。

### 典型示例

LEAD（VLDB 2026）Figure 3：上行展示离线设置；下行展示在线选择与训练集成。跨层箭头展示数据流。

## 5. 设计原则

- **模块化**：每个组件是命名框。用户可追踪组件到对应子节。
- **清晰数据流**：箭头显式，能不交叉就不交叉。
- **层次可见**：颜色、大小或位置区分级别（主组件大；辅助组件小或灰）。
- **名称匹配正文**：图中每个组件名在方法论子节标题中原样出现。如图说"Hotspot Detector"，论文就说"第 3.2 节 Hotspot Detector"。
- **输入输出显式**：图在方法边界展示整体输入和输出。

## 6. 工具推荐

### 首选：draw.io（又称 diagrams.net）或 PowerPoint

- 网格对齐保持整洁。
- 形状库覆盖典型架构组件。
- 导出 PDF 为矢量。

### 次选：Figma 或 TikZ

- Figma 用于精修和团队协作。
- TikZ 用于 LaTeX 集成风格一致性；初始投入高但视觉效果最干净。

### 避免

- 手绘工具（Procreate、GoodNotes）用于早期草图以外的任何用途。输出缺乏对齐，在论文中显得不专业。
- 通用图表自动生成器；它们不理解论文图表惯例。
